At a glance

Almost every technique is one of four verbs applied to the window — write context out, select context in, compress what stays, isolate work into separate windows — resting on a foundations layer of model and serving capabilities. The map below places each ranked technique on that lifecycle.

The framings the field already uses

Several well-known write-ups organise the same techniques in their own way. This report's categories map onto all of them:

  • Write / Select / Compress / Isolate (LangChain, Lance Martin) — The most-reused taxonomy: write context outside the window (scratchpads, memories), select what to pull in (RAG, tool selection, memory retrieval), compress what stays (summarization, trimming), and isolate work across sub-agents, sandboxes and state schemas. Used as the stage vocabulary for this report.
  • Anthropic long-horizon trio + just-in-time retrieval — Context engineering = curating the smallest high-signal token set because attention is finite (context rot). Prescribes system-prompt altitude, tool curation, just-in-time retrieval via lightweight identifiers, and three long-horizon techniques: compaction, structured note-taking (memory files), and sub-agent architectures.
  • Manus lessons: KV-cache hit rate, file system as context, recitation — Production playbook: KV-cache hit rate is the #1 metric (stable append-only prefix), mask tools instead of removing them, use the filesystem as unlimited context with reversible pointers, recite goals via todo.md, keep errors in context, avoid few-shot ruts.
  • 12-Factor Agents: own your context window, small focused agents — Dex Horthy's manifesto (475 HN points): serialize the event log into a custom token-dense format you control (Factor 3), compact errors into context, keep agents to 3-10 steps (Factor 10), and carry state in files across a research -> plan -> implement loop with frequent intentional compaction.
  • Lance Martin's offload / reduce / retrieve / isolate — Practitioner restatement of the LangChain taxonomy from the Latent Space episode and the Manus write-up: offload heavy tool output to disk/state, reduce via compaction and pruning, retrieve just-in-time, isolate with sub-agents; motivated by Open Deep Research burning ~500K tokens per run.
  • Breunig's four failure modes and six fixes — Failure modes (poisoning, distraction, confusion, clash) mapped to remedies: RAG, tool loadout, context quarantine, context pruning, context summarization, context offloading. Amplified by Simon Willison and the 915-point HN thread; reused by nilenso, Digital Applied and many 2026 guides.
  • How long contexts fail (Breunig) — Names context poisoning, distraction (>100K tokens), confusion (too many tools) and clash as the reasons bigger windows do not save you; the diagnostic half of the Breunig framing.
  • MemGPT / LLM-as-operating-system (virtual context management) — The context window is RAM; external storage is disk; the LLM pages data in and out via tool calls (core vs archival/recall memory). Basis of Letta memory blocks, the 'Missing Memory Hierarchy' demand-paging paper, and Karpathy's LLM-OS framing.
  • Mei et al. survey: retrieval/generation, processing, management + RAG/memory/tools/multi-agent — Academic formalization (143 citations) splitting context engineering into foundational components (context retrieval and generation, context processing, context management) and system implementations (RAG, memory systems, tool-integrated reasoning, multi-agent systems), with the Awesome-Context-Engineering companion list.
  • Phil Schmid's seven components of the context window — System instructions, user prompt, short-term history, long-term memory, retrieved information, tool definitions, structured output schema; the post behind the largest HN thread (915 points).
  • Karpathy's definition — 'The delicate art and science of filling the context window with just the right information for the next step' (~14K likes); lists task decomposition, RAG, few-shot examples, summarization and tool-result management as the constituent skills.
  • LangChain 'The rise of context engineering' (dynamic systems) — Harrison Chase: context engineering is building dynamic systems that provide the right information and tools in the right format; most agent failures are context failures.
  • Deep agents recipe (planning tool + filesystem + sub-agents + detailed system prompt) — Harrison Chase's distillation of Claude Code / Manus / Deep Research: a todo/planning tool, a filesystem for offloading, sub-agent delegation for isolation, and a long system prompt; 'the harness matters more than the model' for long-horizon work.
  • Research -> Plan -> Implement, frequent intentional compaction, the 'dumb zone' — Dex Horthy's coding-agent workflow: keep utilization low (quality drops past ~40%), work in phases whose plan/progress files become the handoff, restart with fresh context (Ralph loop) and carry state forward in files.
  • Memory writing / management / reading (Zhang et al. memory survey) — The standard academic framing of agent memory (721 citations): sources, forms (textual vs parametric) and operations (writing, management, reading), with evaluation methods; complemented by the 3D-8Q taxonomy of Wu et al.
  • Hard vs soft prompt compression (Li et al. survey) — Hard methods filter or paraphrase tokens (LLMLingua, Selective Context); soft methods learn compressed vectors (gist tokens, AutoCompressors, ICAE).
  • Share full context / single-threaded agent (Cognition) — Counter-framing to sub-agent isolation: share full traces, avoid parallel actions that carry conflicting implicit decisions, and for very long tasks use a dedicated context-compression model; updated in 2026 to a single-writer principle.

1 Long-term memory systems & memory files

Write · write outPopularity rank #1·47 sources in this survey

Long-term memory keeps what an agent learns outside the context window and pages the relevant slice back in when a task or turn starts. It is the most widely shipped context technique because every multi-session agent needs it: coding assistants read CLAUDE.md, chat products recall user facts, agents resume unfinished work.

Problem it solvesEach session starts with an empty window, so preferences, project facts, and past decisions are lost unless stored deliberately and retrieved on demand.
Lifecycle stagewrite — persist outside the window, page back later
Popularity signals47 sources in this survey. Stars: mem0 63.7k, crewAI 57.4k, cognee 30.1k, graphiti 30.1k, letta 24.3k. Citations: Generative Agents 5,211, MemGPT 1,141, A-MEM 897, Mem0 559. Shipped by Anthropic (memory tool, CLAUDE.md, auto memory), LangGraph/LangMem, Letta, Mem0, Zep, cognee, CrewAI, Google ADK, LlamaIndex.

How it works

Every variant runs one loop: decide what is worth keeping, write it to a store, later select a small slice to inject. They differ in store and writer. MemGPT treats the window like RAM: a small always-present core memory the model edits itself, plus archival and recall tiers it pages in with tool calls. Mem0, CrewAI, and Vertex AI Memory Bank run an LLM over each exchange to extract facts, then add, update, merge, or delete against existing entries. Zep's Graphiti and cognee store facts as a temporal knowledge graph with validity intervals, so superseded facts are invalidated rather than overwritten. Coding agents use the simplest form: markdown files (CLAUDE.md, MEMORY.md, /memories) read at session start. Entries are typed as semantic, episodic, or procedural, and written in the hot path or by background consolidation.

How to achieve it

  1. Match the store to the data. Markdown files suit a single-user coding agent (CLAUDE.md for rules you write, MEMORY.md for notes the model writes); a namespaced vector store (LangGraph, Mem0) suits many users; a temporal graph (Graphiti, cognee) only when facts change over time.
  2. Split memory into an always-in-context core and a paged tier. Keep identity, user profile, and current task in small size-limited blocks the agent edits itself (Letta memory_replace / memory_insert / memory_rethink, or str_replace in the Anthropic memory tool); page everything else in from archival storage by search.
  3. Write through extraction and consolidation, not raw logs. An LLM extracts candidate facts from each exchange, compares them with existing entries, then adds, updates, merges, or skips, so contradictions do not pile up (Mem0; ADK add_session_to_memory).
  4. Tag entries by type and namespace: semantic facts, episodic summaries, procedural instructions, keyed by (user_id, kind), so retrieval can target one kind and procedural memory can be folded into the system prompt.
  5. Retrieve with a scored query and a cap. Combine similarity with recency and importance (the Generative Agents score), keep a handful of hits, and log what was recalled.
  6. Move heavy consolidation off the hot path. A sleep-time or scheduled agent rereads transcripts, rewrites blocks, links related notes (A-MEM), and decays stale entries (MemoryBank's forgetting curve). Measure on LongMemEval or LOCOMO.
from langchain.embeddings import init_embeddings
from langgraph.store.memory import InMemoryStore  # PostgresStore in production

# Long-term store with a semantic index (LangGraph "add memory" docs)
store = InMemoryStore(
    index={"embed": init_embeddings("openai:text-embedding-3-small"), "dims": 1536}
)
ns = ("user-42", "memories")  # namespace = who + what kind of memory

# WRITE: typed entries, from the hot path or a background consolidation job
store.put(ns, "pref-pkg", {"data": "Prefers pnpm over npm", "type": "semantic"})
store.put(ns, "ep-2026-08-19",
          {"data": "Flaky Redis test traced to TTL mismatch", "type": "episodic"})
store.put(ns, "proc-review",
          {"data": "Always run `pnpm test` before opening a PR", "type": "procedural"})

# SELECT: recall a few relevant entries and inject them, never the whole store
hits = store.search(ns, query="which package manager should I use?", limit=3)
facts = "\n".join(f"- [{h.value['type']}] {h.value['data']}" for h in hits)
system_prompt = f"Known facts about this user:\n{facts}"

Variants & tools

  • Letta (MemGPT lineage) — size-limited core blocks pinned in context and edited by the agent; archival and recall memory paged in by tools; sleep-time agents rewrite shared blocks in the background.
  • Mem0 — LLM fact extraction with add/update/merge and an optional graph store; 26% over OpenAI memory on LOCOMO, 91% lower p95 latency.
  • Zep Graphiti — bi-temporal knowledge graph; 94.8% on DMR versus MemGPT's 93.4%, up to 18.5% better on LongMemEval.
  • LangGraph store + LangMem — namespaced put/search/get with an embedding index; LangMem adds semantic, episodic, and procedural managers.
  • Claude Code CLAUDE.md + auto memory — human-written instructions in managed, user, project, and local scopes, @imports, path-scoped .claude/rules/, plus a Claude-written MEMORY.md index.
  • Anthropic memory tool — client-side /memories directory driven by view, create, str_replace, insert, delete, rename (memory_20250818).
  • Google ADK / Vertex AI Memory Bank — add_session_to_memory ingests finished sessions; an LLM consolidates salient facts.

Trade-offs & pitfalls

  • Stale or contradictory entries. Without update and invalidate operations, conflicting facts accumulate and the model picks one arbitrarily; Claude Code's docs say the same of conflicting CLAUDE.md lines.
  • Memory is context, not enforcement. Long files reduce adherence (Claude Code targets under 200 lines; only the first 200 lines or 25 KB of MEMORY.md load). Use hooks for hard rules.
  • Memory poisoning. MINJA plants records through ordinary queries with over 95% injection success. Treat recalled memory as untrusted, reject paths outside /memories, cap sizes, expire unused files.
  • Cost and latency. Extraction adds an LLM call per turn; hot-path writes slow responses, background writes lag a session. Concurrent memory_rethink on a shared block loses updates; designate one writer.
  • Benchmark fragility. LOCOMO and DMR scores depend on judge prompts and retrieval settings; the Zep versus MemGPT DMR gap is 1.4 points. Rerun on your own traffic.

2 Compaction & summarization of history

Compress · shrinkPopularity rank #2·42 sources in this survey

When the transcript nears the window limit, the runtime asks the model to write a structured summary of older turns, swaps it in, and keeps going. It needs no external store, so it ships built in almost everywhere: on by default in Claude Code and Cline, and available as an opt-in reducer, history processor or API option in LangGraph/LangMem, Semantic Kernel, the OpenAI Agents SDK, Pydantic AI, Letta and the Anthropic API.

Problem it solvesAn agent or chat session outgrows the context window, or degrades from context rot, long before the task is finished.
Lifecycle stagecompress — shrinks history in place, no retrieval
Popularity signals42 sources in this survey (second by source count, behind long-term memory at 47); the most frequent technique tag in the corpus (31 tags, twice rag at 15). On by default in Claude Code (142k stars), Cline (66k), LangGraph (40k), Semantic Kernel (28k), OpenAI Agents SDK (29k) and Pydantic AI (19k). 10+ auto-compact issues in anthropics/claude-code.

How it works

A token counter watches the message list. When it crosses a trigger (Claude Code near the model limit, adjustable with /autocompact; Cline's proposed 80 percent; LangMem's max_tokens_before_summary; the Anthropic API's context_token_threshold, default 100,000), the runtime injects a summary prompt as a user turn. The model writes a structured digest: goal, decisions, files touched, progress, next steps. Claude Code's prompt "preserves architectural decisions, unresolved bugs, and implementation details while discarding redundant tool outputs". Older messages are deleted and the digest takes their place; recent turns stay verbatim. Recursive variants (Wang et al.) fold the previous summary plus new turns into a fresh one, and LangMem's RunningSummary tracks summarized_message_ids so nothing is summarized twice. Content outside the message history (system prompt, CLAUDE.md) reloads from disk; anything that existed only in conversation survives only if the summary mentions it.

How to achieve it

  1. Choose the trigger and counter. Summarize at a token threshold well below the hard limit so the summary call still fits, and keep the last N turns or tool-call groups untouched (LangMem max_tokens_before_summary, Anthropic compaction_control.context_token_threshold).
  2. Write the compaction prompt as a schema: goal, constraints, decisions with rationale, files modified, completed versus pending work, open bugs, next steps. Anthropic's guidance: maximize recall first, then iterate toward precision.
  3. Protect structural invariants. Never separate a tool call from its result (providers reject orphaned results), keep the system message, and re-inject durable instructions (project-root CLAUDE.md, skill bodies) from disk.
  4. Prefer intentional compaction at task boundaries. Run /compact focus on ... before a new task, or write a handoff or plan file and /clear. Horthy's research-plan-implement loop compresses roughly 100k tokens of research into a 10k-token plan, verified by a human, then implements in a fresh context.
  5. Offload compression: subagents return 1,000-2,000 token digests, Letta sleep-time agents rewrite shared memory blocks every N steps, and a cheaper model (compaction_control["model"] = "claude-haiku-4-5") can write the summary.
  6. Eval against the alternatives on your own task. Observation masking and cached full history both beat summarization in published tests; track recall, cost per turn and trajectory length.
from typing import Any
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, START, MessagesState
from langgraph.checkpoint.memory import InMemorySaver
from langmem.short_term import SummarizationNode

model = ChatOpenAI(model="gpt-4o")
class State(MessagesState):
    context: dict[str, Any]   # holds the RunningSummary between turns

summarize = SummarizationNode(
    model=model.bind(max_tokens=256),
    max_tokens=4096,                 # budget for what the model sees
    max_tokens_before_summary=4096,  # trigger once history exceeds this
    max_summary_tokens=256,
)

def call_model(state):
    # summarized_messages = running summary + recent verbatim turns
    return {"messages": [model.invoke(state["summarized_messages"])]}

graph = StateGraph(State)
graph.add_node("summarize", summarize)
graph.add_node("call_model", call_model)
graph.add_edge(START, "summarize")
graph.add_edge("summarize", "call_model")
app = graph.compile(checkpointer=InMemorySaver())
app.invoke({"messages": "hi, my name is bob"}, {"configurable": {"thread_id": "1"}})

Variants & tools

  • Claude Code /compact, /autocompact, /clear, /rewind — auto-compacts near the limit; re-injects project-root CLAUDE.md and invoked skills, drops the skill index and nested CLAUDE.md.
  • Anthropic API compaction_control — SDK tool_runner summarizes at context_token_threshold; server-side compaction recommended on Opus 4.6 and newer.
  • LangMem SummarizationNode / RunningSummary — LangGraph node keeping a running summary plus recent turns under a token budget.
  • Semantic Kernel ChatHistorySummarizationReducer — truncates to target_count, summarizes the removed messages into one inserted message; optional auto_reduce.
  • Cline Auto Compact — threshold-triggered condensation; community spec: configurable 80 percent trigger, cheaper summarizer model, pre-compaction snapshot.
  • Letta sleep-time agents — enable_sleeptime=True spawns a background agent that rewrites shared memory blocks every sleeptime_agent_frequency steps.
  • Cognition context-compression model — a fine-tuned model whose only job is to compress action history into key details, events and decisions.

Trade-offs & pitfalls

  • Mid-task compaction loses state. Issue #10948: lost file-modification history, decisions and planned-versus-implemented status, then hallucinated progress; Cline #5790: completed work redone. Workarounds: /rewind, checkpoint files, compacting only at boundaries.
  • Summaries break prompt caching. In Bouchard's 2026 tutor evals, full cached history cost $0.11 per turn with 92-100 percent recall versus $0.24 and 38-58 percent for the clearing-plus-summary preset; capping tool output size cut cost 38 percent without rewriting the prefix.
  • Summarization can lengthen runs. On SWE-bench Verified, masking old observations matched LLM summaries (54.8 vs 53.8 percent on Qwen3-Coder 480B) at lower cost ($0.61 vs $0.64), and summaries lengthened trajectories about 15 percent.
  • Not everything reloads. In Claude Code the skill index, nested CLAUDE.md files and path-scoped rules are summarized away; keep must-survive rules in the project-root CLAUDE.md and at the top of SKILL.md (large skills truncate from the end).
  • Compaction quality is unmeasured. Anthropic warns that over-aggressive prompts drop "subtle but critical context"; treat the summary prompt as code with its own recall eval.

3 Model & infra foundations: long windows, prompt caching, KV cache

Foundations · beneathPopularity rank #3·43 sources in this survey

What the model and serving stack give you before any application-level trick: 1M-token nominal windows, vendor prompt caching that bills repeated prefixes at a tenth of list price, and the KV-cache machinery underneath (paged memory, prefix reuse, eviction, quantization, bounded-memory attention). It is nearly free and sets the ceiling for every other technique.

Problem it solvesLong prompts cost quadratic prefill and linearly growing KV memory, and models reliably use only part of their nominal window.
Lifecycle stagefoundations — substrate every later stage inherits
Popularity signals43 sources in this survey; Lost in the Middle ~4.7K citations, StreamingLLM ~2.3K, RULER ~1.2K; LMCache 11.2K GitHub stars; vLLM and SGLang cache prefixes by default; Anthropic, OpenAI and Gemini all sell 1M windows plus ~0.1x cached input; Chroma's "context rot" is the practitioner term.

How it works

Three layers stack. The model fixes the nominal window: RoPE rescaling such as YaRN stretches a pretrained model to 128K, and Ring Attention shards longer sequences across devices. Effective length is shorter and position-dependent: Lost in the Middle shows a U-shaped accuracy curve, RULER found only half of 17 models claiming 32K+ held up at 32K, and Chroma measured non-uniform decay across 18 frontier models. The serving engine stores a key/value pair per token per layer. PagedAttention keeps them in fixed blocks so identical prefixes share memory; prefix caching (vLLM hashes blocks, SGLang keeps an LRU radix tree, LMCache spills to CPU, disk and remote stores) skips prefill for any prefix seen before, and vendor prompt caching sells the same mechanism. When KV still does not fit, eviction (attention sinks plus a recent window, heavy hitters, SnapKV, PyramidKV) or KIVI's 2-bit quantization shrinks it, and hybrid designs (Gemma 3's 5:1 local-global layers, Mamba/Jamba) bound it.

How to achieve it

  1. Measure effective context first: run RULER or a NIAH variant with distractors at your real prompt lengths and budget for the length where accuracy stays flat, not the advertised one.
  2. Order every prompt for the cache: tools, system, stable context, then the volatile turn. On Claude, mark the last stable block with cache_control (reads bill at 0.1x after a 1.25x five-minute or 2x one-hour write); OpenAI caches prefixes of 1,024+ tokens implicitly.
  3. Verify hits from usage fields (cache_read_input_tokens, cached_tokens), never from the invoice; prompts under the model minimum (512 to 4,096 tokens on Claude) silently do not cache.
  4. Self-hosting: leave vLLM prefix caching on or serve with SGLang, add LMCache to offload KV to CPU, SSD or Redis and share it across replicas, and pin same-prefix sessions to one replica.
  5. When KV memory binds, quantize first (KIVI: 2.6x lower peak memory, up to 4x batch) and evict second; re-benchmark SnapKV or PyramidKV budgets on your own reasoning and instruction-following tasks.
  6. Route rather than stuff: queries needing a small slice of a corpus go to retrieval, cross-document synthesis stays on the long window, and Self-Route lets the model abstain to the long path.
import anthropic

client = anthropic.Anthropic()

# Stable prefix first (tools -> system -> messages); put the breakpoint on the
# LAST block that is identical across calls. Everything after it bills as input.
SYSTEM = [
    {"type": "text", "text": "You review pull requests for the repository below."},
    {
        "type": "text",
        "text": REPO_SNAPSHOT,  # must exceed the model minimum (1,024 tokens on Sonnet 4.6)
        "cache_control": {"type": "ephemeral", "ttl": "1h"},  # 2x write, 0.1x reads for 1h
    },
]

def ask(question: str) -> str:
    resp = client.messages.create(
        model="claude-sonnet-4-6",  # 1M window, no beta header since March 2026
        max_tokens=16000,
        system=SYSTEM,
        messages=[{"role": "user", "content": question}],
    )
    u = resp.usage  # first call: cache_creation_input_tokens > 0
    print(u.cache_creation_input_tokens, u.cache_read_input_tokens, u.input_tokens)
    return resp.content[0].text

Variants & tools

  • vLLM automatic prefix caching — KV blocks keyed by hash(prefix + block); zero-refcount blocks evicted LRU-first.
  • SGLang RadixAttention — LRU radix tree over token sequences with cache-aware scheduling.
  • LMCache — tiered KV offload (GPU, CPU, SSD, Redis/Mooncake/S3), cross-instance sharing and prefill-to-decode transfer.
  • OpenAI prompt caching — implicit reuse of the longest seen prefix from 1,024 tokens in 128-token steps.
  • PyramidKV — layer-wise KV budgets; matches the full cache at 12% on LongBench; same family as H2O and SnapKV.
  • KIVI — tuning-free 2-bit KV quantization, per-channel keys and per-token values; 2.35 to 3.47x throughput.
  • Gemma 3 local-global attention — five 1,024-token sliding-window layers per global layer; KV share of memory drops from ~60% to ~15%.
  • Mamba — selective state-space model with a fixed-size state instead of a growing KV cache; Jamba interleaves it with attention.

Trade-offs & pitfalls

  • Nominal is not effective: half of RULER's 17 models failed at 32K, middle-of-context facts are the weakest, and Chroma found low needle-question similarity and coherent haystacks speed up decay.
  • Caching is positional: one byte changed in tools or system invalidates everything after it, and a timestamp at the top guarantees zero hits. A five-minute cache pays back after one reuse, a one-hour cache only after two.
  • Eviction hides damage: StreamingLLM states it does not extend the window or add memory, and heavy-hitter or observation-window policies tuned on QA can drop the instruction or step a later reasoning turn needs. Quantization degrades more gracefully.
  • The physics still bill you: a 900K-token Claude request costs the same per token as a 9K one, still roughly $3 to $5 of input per call before caching. Bounded-memory models trade exact far-back recall for that saving.

4 Retrieval & just-in-time context loading

Select · pull inPopularity rank #4·26 sources in this survey

Keep the corpus outside the model and pull in only the slice a step needs: document chunks, code symbols, tool definitions, memories, MCP resources. RAG is the oldest context trick and still the main cost and attention control even with million-token windows; coding agents, MCP hosts and Claude's tool search all ship a form of it.

Problem it solvesRecall degrades as tokens pile up (context rot) and cost scales with every token, yet the facts, code or tools a step needs are a tiny fraction of what is available.
Lifecycle stageselect — fetches context at use time
Popularity signals26 sources in this survey (rag tag 15, retrieval 7); llama_index 51.8k stars, langchain ~145k, aider ~35k; Agentic RAG survey 393 citations, Self-Route 169; shipped in Claude Code (grep/glob), aider, Cursor, Windsurf, MCP hosts and Anthropic's tool search tool.

How it works

One idea, several forms: heavy data stays outside the window, a cheap pointer stays inside. Classic RAG indexes chunks and injects the top-k hits; advanced and modular RAG add query rewriting, hybrid BM25 plus vector search, metadata filters, re-ranking and routing across specialized indices. Agentic RAG hands the loop to the model: plan, retrieve, reflect on sufficiency, retrieve again or switch source (corrective and adaptive loops, single or multi-agent). Just-in-time retrieval drops the index for lightweight identifiers the agent follows itself (file paths, URIs, glob, grep, head, tail), disclosing detail progressively. The same pattern covers tool definitions (search plus deferred loading), memories (vector or graph lookup) and MCP resources, where the host, not the model, decides which URIs enter context. Self-Route adds a switch: answer from retrieved chunks when they suffice, otherwise fall back to the full long context.

How to achieve it

  1. Pick the unit of retrieval and index it. Chunk documents with metadata; for code, parse the repo with tree-sitter and rank symbols by incoming references (aider's repo map fits the top signatures into about 1k tokens via --map-tokens); for tools, index names, descriptions and argument descriptions.
  2. Build retrieval evals before tuning. Generate synthetic question-to-chunk pairs, score retriever precision and recall apart from answer quality, then cluster real queries (even 100 reveal patterns) to split content gaps from capability gaps.
  3. Retrieve hybrid and re-rank. Combine full-text or grep with embeddings, filter on extracted metadata, re-rank candidates, and route queries to specialized indices instead of one flat store.
  4. Give the agent handles, not payloads. Expose read, grep and glob tools, file paths and MCP resource URIs; preload a small high-value set (a rules file, the 3 to 5 hottest tools) and defer the rest to on-demand search.
  5. Close the loop agentically. After each retrieval the model judges sufficiency, reformulates or switches source, and stops at a hard iteration cap.
  6. Route between retrieval and raw long context. Try RAG first; if the model declares the chunks insufficient, resend with the full document. Track per-query cost and retrieval hit rate.

  • Anthropic tool search tool — defer_loading: true plus a regex or BM25 search tool; cuts a ~55k-token multi-server tool prefix by over 85%, caching intact.

  • Self-Route — per-query routing between RAG and long context; 65% (Gemini-1.5-Pro) and 39% (GPT-4o) cost reduction at near long-context quality.

Trade-offs & pitfalls

  • Retrieval quality is the ceiling. When affordable, long context beats RAG on average (Li et al.); retrieval wins on cost, so measure the gap and route rather than pick a side.
  • Embedding search degrades as the corpus grows. Windsurf calls it unreliable at scale and layers grep, AST parsing, knowledge graphs and re-ranking on top.
  • Runtime exploration is slower than precomputed retrieval, and an unguided agent wastes context misusing tools or chasing dead ends (Anthropic). Cap iterations; preload the predictable part.
  • Tool overload is real: DeepSeek-v3 confuses tools above 30 and nearly always fails past 100; Llama 3.1 8b fails with 46 tools but succeeds with 19 (Breunig). Keep 3 to 5 hot tools loaded, never defer the search tool itself.
  • Evaluate the retriever, not just the answer. Without synthetic precision/recall sets and query clustering you tune blind; position effects (lost in the middle) can hide good hits.

5 Context offloading and cache-friendly prompt structure

Write · write outPopularity rank #5·28 sources in this survey

Treat the context window as a deliberately laid-out, append-only buffer and everything else as external state. Raw tool output, plans and notes go to files with pointers left behind; the prompt prefix never changes, so the provider's KV cache keeps hitting. Manus, Claude Code, Cline and LangChain's Deep Agents converge on this shape.

Problem it solvesAgent transcripts bloat with tool output and are re-sent every turn at full price, so the window must be both small and byte-stable.
Lifecycle stagewrite — externalize state before it enters the window
Popularity signals28 sources in this survey (prompt-caching 8, context-offloading 5, token-budgeting 4). Manus's post was among 2025's most reshared; Anthropic's drew 148 HN points; 12-Factor Agents drew 475 HN points and two conference talks. Shipped in Manus, Claude Code, Cline, LangChain Deep Agents and all three vendor caching APIs.

How it works

Every turn re-sends the whole transcript, and Manus reports an input-to-output ratio near 100:1, so input tokens dominate cost and latency. Providers serve a repeated prompt prefix from KV cache at about a tenth of the price: Anthropic bills cache reads at 0.1x and writes at 1.25x, OpenAI applies an automatic cached-input discount (no write premium; the rate varies by model), and Gemini 2.5+ caches implicitly. Keep the prefix identical: static system prompt first, no timestamps, deterministic serialization, append-only events, a fixed tool list. Then shrink the window without editing that prefix: write tool output to the sandbox filesystem and leave a restorable path or URL, keep the plan in a todo.md the agent rewrites at the tail of the context so goals stay in recent attention, and let grep or sub-agents re-read files on demand.

How to achieve it

  1. Lay the prompt out in stability order: tools, system prompt, canonical examples, then messages. Strip timestamps and request IDs, and pin serialization (key order, whitespace) so identical state produces identical bytes.
  2. Put a cache breakpoint on the last constant block (Anthropic cache_control, OpenAI prompt_cache_key, Gemini explicit CachedContent) and log cache_read_input_tokens or cached_tokens on every request. Treat hit rate as an SLO.
  3. Offload tool output: write the raw result to a file and keep a short pointer (path, size, first lines) in the event log; restore with read_file or grep only when needed. Compact stale results to pointers first; summarize only when that runs out.
  4. Recite goals in a todo.md or NOTES.md the agent rewrites after each step. Anthropic's note-taking agent kept exact tallies across thousands of steps and resumed after context resets from its notes.
  5. Curate the action space instead of swapping it: keep tool definitions fixed, use consistent name prefixes such as browser_ and shell_, and constrain choice with logit masking or response prefill rather than adding or removing tools mid-task.
  6. Own the serialization: write your own thread_to_prompt() over an event log (12-Factor, Factor 3) so you decide density and how errors appear. Keep failed calls in, add small variation to avoid few-shot ruts, and budget utilization (Cline: 70-80% fill; Horthy: about 40%).
import anthropic, hashlib, pathlib

client = anthropic.Anthropic()
SCRATCH = pathlib.Path("scratch"); SCRATCH.mkdir(exist_ok=True)
events = []  # append-only; never rewrite earlier entries

def offload(tool_name: str, raw: str) -> str:
    """Write raw tool output to disk; keep a restorable pointer in context."""
    path = SCRATCH / f"{tool_name}-{hashlib.sha1(raw.encode()).hexdigest()[:10]}.txt"
    path.write_text(raw)
    return (f"<{tool_name}_result path=\"{path}\" bytes={len(raw)}>\n"
            f"{raw[:400]}\n...(truncated; read_file to restore)\n</{tool_name}_result>")

    events.append({"role": "user", "content": user_text})
    resp = client.messages.create(
        model="claude-opus-5",
        max_tokens=1024,
        tools=TOOLS,  # fixed list, never pruned mid-task
        system=[{"type": "text", "text": SYSTEM_PROMPT,  # static: no clock, no IDs
                 "cache_control": {"type": "ephemeral"}}],  # breakpoint on stable prefix
        messages=events,
    )
    events.append({"role": "assistant", "content": resp.content})
    u = resp.usage
    total = u.cache_read_input_tokens + u.cache_creation_input_tokens + u.input_tokens

  • Manus — stable prefix, logit-masked tools, filesystem as context, todo.md recitation.
  • LangChain Deep Agents — write_todos middleware, virtual filesystem, sub-agents; LangChain's default harness.
  • 12-Factor Agents, Factor 3 — custom token-dense event-log serialization instead of the framework message list.
  • Anthropic context editing — server-side clear_tool_uses swaps old tool results for placeholders past a token trigger.
  • Anthropic, OpenAI and Gemini prompt caching — explicit breakpoints, automatic prefix caching with routing keys, and implicit plus explicit caches.
  • Cline — context progress bar and a new_task handoff that preloads only rule-selected state.
  • TokenPilot — research framework that compacts and evicts context while keeping prefix cache hits.
  • Harrison Chase, "Filesystems for context engineering!" — a filesystem as the pragmatic primitive for agent state.

Trade-offs & pitfalls

  • The cache is fragile: one changed token, a reordered tool, an added image or a new tool_choice invalidates everything after it. Minimum cacheable sizes vary (512-4,096 tokens on Claude, 1,024 on OpenAI, 2,048-4,096 on Gemini) and default TTLs are minutes; verify hits from usage fields.
  • Compaction and caching pull in opposite directions: rewriting old messages breaks the prefix hash. Compact rarely, at breakpoints, and prefer pointer substitution to summaries; TokenPilot reports 56 to 87 percent cost reductions from co-designing the two.
  • Pointers only help if restoration is cheap and the model knows to use it; you trade tokens for extra tool calls. A summary that drops the one relevant detail is irreversible, so keep the raw file.
  • Logit masking assumes you control decoding or the provider exposes prefill. On the Claude API, toggling tool_choice per turn still invalidates the cached messages prefix, so steer through the prompt where possible.
  • Recitation costs tokens every turn: Manus found about a third of its actions went to task-list updates before moving planning into a dedicated planner agent.

6 Isolation via sub-agents, multi-agent and sandboxed state

Isolate · splitPopularity rank #6·27 sources in this survey

Give each unit of work its own context window. An orchestrator keeps the plan; sub-agents explore with clean context and hand back a short summary; heavy objects stay in sandboxes or state fields the model never sees. People use it because isolation removes context rot and lets exploration run in parallel, at the price of tokens and coordination.

Problem it solvesOne long thread fills with stale tool output, loses its plan, and cannot explore several branches at once.
Lifecycle stageisolate — context is partitioned, not shrunk
Popularity signals27 sources in this survey (21 tag instances). Shipped natively in Claude Code (142,118 stars), the Claude Agent SDK (7,942), LangChain Deep Agents and Google ADK; CrewAI (57,392) and AutoGen (60,540) appear via their context docs. One of Anthropic's three long-horizon techniques, LangChain's "isolate", Breunig's "context quarantine", 12-factor Factor 10 (HN 475 points). Anchored by Anthropic's research system, Cognition's "Don't Build Multi-Agents" and its 2026 revision.

How it works

The lead agent holds the goal and the plan, splits the task, and spawns sub-agents that each start a fresh conversation: they receive their own system prompt plus the task string, never the parent's history. A worker may spend tens of thousands of tokens searching or reading files, then returns a 1,000-2,000 token summary that lands in the parent as one tool result. Anthropic's research system runs 3-5 workers in parallel, each with its own tools, and the lead writes its plan to memory so truncation past 200K tokens cannot lose it. The same idea works inside one agent: LangGraph state schemas expose only selected fields to the model each turn, code sandboxes hold images and dataframes and pass handles instead, and Google ADK's agents-as-tools plus include_contents='none' stop history from cascading down an agent hierarchy.

How to achieve it

  1. Check the task is parallelizable and worth the cost. Anthropic reports a 90.2% gain on research evals at about 15x the tokens of chat, and says most coding tasks have few parallel pieces.
  2. Define each sub-agent with a narrow description, its own system prompt, a restricted tool list and, where possible, a cheaper model. A reviewer gets Read, Grep, Glob only; a test runner gets Bash.
  3. Put everything the worker needs in the task prompt: file paths, error messages, decisions already taken, and the output format and length you want; it sees none of the parent's history.
  4. Have workers return condensed findings (1-2K tokens) and keep the lead on synthesis. Persist the lead's plan to a file or memory tool so a truncated window cannot lose it.
  5. Keep writes single-threaded. Let extra agents review, research or advise while one thread owns edits (Cognition, 2026). For sequential work, prefer a fresh context per iteration (the Ralph loop) over parallel writers.
  6. Cap depth, concurrency and spend (CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH, CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS, max_budget_usd), and route large objects through sandboxes or state fields rather than into prompts.

                        "Explore the repo and answer the question. Return at most 1500 tokens: "

                 "CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS": "5"},

            print(msg.result)  # only the worker's final summary reached this context

Variants & tools

  • Claude Code / Agent SDK subagents — AgentDefinition with own prompt, tools, model and permissions; only the final message returns; depth, concurrency and budget caps.
  • Anthropic lead researcher + subagents — orchestrator-workers for research; 3-5 parallel workers, plan saved to memory.
  • LangChain Deep Agents — harness recipe: planning tool, file system for offloading, sub-agent delegation, detailed prompt.
  • Google ADK — agents-as-tools, include_contents scoping, artifacts as handles, event filtering between agents.
  • LangGraph state schemas and code sandboxes — expose only chosen state fields per turn; keep images and large objects in the execution environment.
  • Cognition code-review loop and smart friend — single-writer patterns where extra agents add reasoning, not edits.
  • Ralph loop — sequential isolation: each iteration is a new process with an empty window; it reads specs from disk, does one task, exits.
  • Context quarantine (Breunig) — the general name for dedicated threads per sub-problem.

Trade-offs & pitfalls

  • Token cost. Multi-agent runs use roughly 15x the tokens of chat, and token usage explains about 80% of performance variance in Anthropic's evals; reserve the pattern for high-value tasks.
  • Lost shared context. Parallel workers make implicit decisions that conflict (Cognition's Flappy Bird example: one worker builds a Mario background, another a bird with no physics). Coding rarely parallelizes cleanly; keep one writer.
  • Under- and over-specification. Managers tend to over-prescribe, children assume shared state, and cross-agent messaging does not happen on its own (Cognition, 2026). A worker only knows what its task string says.
  • Context explosion down the tree. If every agent forwards its full history, cost and noise compound (Google). Pass handles and summaries, and scope include_contents.
  • Control and trust. The parent may paraphrase worker output, that output can carry instruction-shaped text (treat worker output as untrusted data), and spawn trees grow unless depth, concurrency and spend are capped.

7 Pruning, trimming & context editing

Compress · shrinkPopularity rank #7·19 sources in this survey

Pruning deletes context instead of rewriting it: keep the last N turns or tokens, blank out old tool outputs, drop stale reasoning blocks, or let the API clear tool results once a threshold is crossed. It is deterministic, needs no extra model call, and can be prompt-cache friendly, so it is the cheapest lever most teams reach for first.

Problem it solvesIn agent loops, tool outputs and reasoning blocks grow fastest and crowd out the instructions and recent state the model needs.
Lifecycle stagecompress — shrinks history without a model call
Popularity signals19 sources in this survey. Shipped by Anthropic (context editing API), LangGraph (~40k stars), AutoGen (~60k), LlamaIndex (~52k), OpenAI Agents SDK (~29k), Semantic Kernel (~28k), Vercel AI SDK (~26k), Pydantic AI (~19k). JetBrains' Complexity Trap (SWE-bench Verified): masking cut cost 52-56% and matched summarization; Anthropic reports 84% fewer tokens on a 100-turn web-search eval.

How it works

Every variant applies a deterministic rule to the message list before each model call. Sliding windows keep the most recent N messages (AutoGen BufferedChatCompletionContext, Semantic Kernel's truncation reducer) or the most recent tokens (LangGraph trim_messages with strategy="last"). Observation masking keeps every user and assistant turn but replaces tool outputs older than the last M turns with a one-line placeholder (JetBrains used M=10). Anthropic's context editing does this server-side: once input tokens (default 100k) or tool-use count pass a trigger, the API clears all but the last keep tool results (default 3), optionally removing at least clear_at_least tokens per edit so each cache invalidation is worth it. Thinking-block clearing is a separate strategy with its own keep count. Dropped content is gone for the model, so pruning is often paired with a memory flush (LlamaIndex) or a memory tool.

How to achieve it

  1. Measure what grows. Log tokens per message role over a few real runs; tool results usually dominate, so target those first.
  2. Pick the rule and unit: last-N turns for chat (OpenAI's TrimmingSession groups tool calls with their user turn), a token budget for variable-length tool output (trim_messages(max_tokens=..., token_counter=count_tokens_approximately)), or observation masking for coding agents that can re-read files.
  3. Preserve structural invariants: never orphan a tool result from its call, start the window on a user message (start_on="human"), and keep the system prompt. pruneMessages and Semantic Kernel reducers handle pairing; a hand-rolled DSPy History or Pydantic AI processor does not.
  4. Trigger on live counts. Read usage from the previous response (Pydantic AI ctx.usage.total_tokens, Anthropic trigger: input_tokens) and clear in large chunks so the cache prefix is invalidated once, not every turn.
  5. Protect what cannot be re-fetched: whitelist tools whose output must stay verbatim (exclude_tools), or flush pruned turns into a memory block or notes file first (LlamaIndex token_flush_size, Anthropic memory tool).
  6. Compare against the unpruned baseline on your own traces (solve rate, cost, trajectory length); if quality drops, widen the keep window before trying summarization.

  • LangGraph trim_messages + RemoveMessage — token-budget trimming in a node, plus deletion of message ids (or REMOVE_ALL_MESSAGES) from graph state.
  • Vercel AI SDK pruneMessages — strips reasoning and tool parts with 'all', 'before-last-message', 'before-last-N-messages' or per-tool arrays.

  • Deletion is blind. Masking works on SWE-bench because files can be re-read; one-shot API results cannot be. Exclude those tools or flush to memory first.

  • Cache effects cut both ways. Clearing invalidates the prompt-cache prefix at the edit point, so clear rarely and in large chunks; kept thinking blocks preserve cache hits, cleared ones do not.
  • Pure trimming loses the thread in long chats; the OpenAI cookbook reserves summarization for when continuity matters.
  • Complex is not automatically better. In the JetBrains study summarization lengthened trajectories 13-15% and a critic-enhanced variant raised cost about 25% with no gain.

How it works

Hard methods delete from the prompt text. LLMLingua runs a small causal LM over the prompt and scores each token by perplexity; low-surprise tokens are dropped. A budget controller first allocates a ratio per segment (instruction, demonstrations, question), then token-level compression runs iteratively so later deletions condition on earlier ones. LongLLMLingua makes the scoring question-aware with contrastive perplexity, ranks whole documents, reorders them so the best sit at the edges, and gives higher-ranked documents more budget. LLMLingua-2 distills GPT-4 keep/drop labels into a bidirectional token classifier: faster, task-agnostic, and no 7B scorer. RECOMP trains a compressor for retrieved passages, extractive or abstractive, that may return an empty summary so the model answers unaugmented. Soft methods (gist tokens, AutoCompressors, ICAE) fine-tune the model to condense text into a handful of vectors it attends to instead of the tokens.

How to achieve it

  1. Decide what is compressible. Retrieved passages, demonstrations and old history are safe targets; keep the instruction and the user question verbatim (LLMLingua's budget controller spends most of the ratio on demonstrations).
  2. Pick a compressor by cost. LLMLingua-2's XLM-RoBERTa classifier runs on CPU and is 3-6x faster than perplexity scoring with a 7B model; use LongLLMLingua when you need question-aware ranking and reordering for long RAG prompts.
  3. Set the budget with rate or target_token. Start at 2-4x, and pass force_tokens so newlines, punctuation and numbers survive; the papers' 20x figures come from verbose few-shot prompts, not dense facts.
  4. For RAG, wire it behind the retriever: LangChain ContextualCompressionRetriever + LLMLinguaCompressor, or LlamaIndex LongLLMLinguaPostprocessor, with reorder_context="sort" and a dynamic ratio to counter lost-in-the-middle.
  5. Evaluate per ratio on your own task. Plot accuracy against compressed tokens and include the compressor's wall-clock time; degradation is non-linear, so find the knee rather than copying a ratio from a paper.
  6. Use soft methods only if you fine-tune and serve the model yourself. Gisting, ICAE and AutoCompressors need training, are tied to one base model, and pay off for repeated fixed prefixes you can cache, not for ad hoc content.

Trade-offs & pitfalls

  • Compression is not free. Scoring a 10k-token prompt with a 7B model can cost more than it saves; the survey notes gains only materialize for long prompts or outputs. LLMLingua-2 exists largely to fix this.
  • Deleting tokens breaks grammar and produces an input distribution the target model never saw. Numbers, names and code are the first casualties; protect them with force_tokens and never compress the question.
  • Abstractive compression hallucinates at high ratios. A 2024 characterization study found query-aware extractive methods most reliable, with accuracy falling off a cliff past a threshold rather than degrading linearly.
  • Soft prompts do not transfer. Gist, ICAE and AutoCompressor vectors are tied to one base model, must be retrained on upgrades, and cannot be sent to a hosted API; gisting's 26x token compression delivered only a 4.2% wall-clock gain.
  • It can fight prompt caching. Compressing a stable system prefix changes its bytes and invalidates provider-side caches; compress volatile content and leave cached prefixes untouched.

9 Vendor-managed conversation state and server-side compaction (OpenAI, Gemini)

Write · write outAddendum · added by the completeness check·12 sources in this survey

Instead of re-sending the whole transcript every turn, you hand the provider an id and it replays, stores and, on request, compacts the thread. OpenAI does this with previous_response_id, the Conversations API and /responses/compact; Gemini does it with the Interactions API and previous_interaction_id. Teams use it to cut payloads, raise cache hits and skip writing a summarizer.

Problem it solvesShipping the full transcript on every turn grows linearly and eventually overflows the window; vendor-held state removes the shipping and gives a one-parameter compaction instead of a hand-built summarizer.
Lifecycle stagewrite — provider persists, then compacts, the thread
Popularity signals12 sources in this survey; first-class API surface at OpenAI (Responses, Conversations, compaction, mirrored on Azure) and Google (Interactions API, GA June 2026); wrapped by OpenAI Agents SDK sessions, LangChain and Agno; open feature requests in Vercel AI SDK, pydantic-ai and opencode.

How it works

OpenAI's Responses API offers three modes. Manual: you send the full input array, including encrypted reasoning items. Chained: you send only the new message plus previous_response_id; the server replays the stored chain, but every prior input token is still billed each turn, and stored responses expire after 30 days unless store=false. Persistent: a Conversation object with its own id holds items (messages, tool calls, tool outputs) with no 30-day TTL and is prepended to each request. On top of either, context_management=[{"type":"compaction","compact_threshold":N}] makes the server swap old items for an opaque, encrypted compaction item once the rendered context crosses N tokens; /responses/compact does the same on demand for a history you hold yourself. Gemini's Interactions API mirrors the chained mode: previous_interaction_id, store=true by default, 55-day (paid) or 1-day (free) retention, and better implicit-cache hits than resending history.

How to achieve it

  1. Pick a mode. Use manual arrays when you need full control, previous_response_id for simple chains, and conversation= when the thread must survive sessions or devices. On Gemini, call interactions.create with previous_interaction_id (google-genai 2.3.0 or later).
  2. Decide storage. Keep store=true if you want to continue by id. Set store=false for zero data retention, and then carry every output item yourself, including encrypted reasoning and compaction items.
  3. Turn on server compaction. Add a context_management compaction entry with a compact_threshold below the model window (OpenAI's examples use 200,000). Keep the compaction item in the window and never prune by hand when chaining by id.
  4. For a self-held history, call responses.compact when your own trigger fires (the Agents SDK default is ten non-user items) and treat the returned output as the canonical next window.
  5. Budget tokens explicitly. On Gemini call count_tokens before sending and read usage.total_cached_tokens after; on OpenAI set truncation="auto" as a last-resort guard so an overflow drops the middle instead of returning HTTP 400.
  6. Re-send interaction-scoped settings each turn (Gemini: tools, system_instruction, generation_config) and keep your own durable record of thread ids, because retention windows expire.

  • OpenAI Conversations API — durable conversation object whose items (messages, tool calls, outputs) are prepended to each Responses call; no 30-day TTL.
  • OpenAI /responses/compact — stateless, ZDR-friendly endpoint that returns a shorter window containing an encrypted compaction item.
  • OpenAI Agents SDK Sessions — OpenAIConversationsSession delegates history to the Conversations API; OpenAIResponsesCompactionSession wraps any session and calls responses.compact on a trigger.

  • Azure OpenAI Responses API — same surface on Azure, including context_management compaction and responses.delete.
  • Gemini Interactions API — previous_interaction_id, store, tiered retention, background execution; replaces generateContent for new projects.

Trade-offs & pitfalls

  • Billing does not shrink. A previous_response_id chain still bills all prior input tokens every turn; only compaction reduces the rendered context, and caching lowers the price, not the count.
  • There is no token-cap knob for chains. Developers asked for an Assistants-style last_messages limit in July 2025 and got no staff answer; without truncation="auto" or compaction, overflow is a 400 error.
  • State is opaque. Compaction items are encrypted and "not intended to be human-interpretable"; you cannot inspect or edit what the model kept, and the thread is not portable across vendors.
  • Retention differs per vendor: OpenAI responses expire at 30 days, Gemini interactions at 55 days (paid) or 1 day (free); Gemini store=false disables id continuation and background execution, and Interactions still lacks explicit caching and Batch.
  • Mixing modes breaks things. Do not pair OpenAIResponsesCompactionSession with OpenAIConversationsSession; do not prune manually when chaining by id; with stateless arrays drop only items that precede the latest compaction item.

10 Token accounting & context observability: measure before you budget

Foundations · beneathAddendum · added by the completeness check·14 sources in this survey

The measurement layer under every other technique here: count what a request will cost before sending it, read the provider's usage object after, attribute the total to system prompt, tool schemas, history and tool results, and alert when utilization crosses a line. Without it, "keep utilization around 40-60%" is a guess, not a control.

Problem it solvesBudgeting, compaction and pruning rules all assume you know utilization per turn and per component; most agent stacks never measure it.
Lifecycle stagefoundations — precondition for compress, select and isolate decisions
Popularity signals12 sources in this survey; free count endpoints from Anthropic, Gemini and Bedrock; tiktoken for OpenAI; OpenTelemetry gen_ai.usage.* adopted by Langfuse, LangSmith, Arize and GitHub Copilot; Claude Code ships /context.

How it works

Three measurements, taken at different times, answer different questions. Before a call, a count endpoint (Anthropic count_tokens, Gemini countTokens) or a local tokenizer (tiktoken, OpenAI models only) returns an estimate for the exact payload, including system prompt, tool definitions, images and PDFs; dividing by the model's input limit gives utilization. After a call, the response usage object is the billed truth: input, output, cache-read and cache-write tokens, plus reasoning tokens on some providers. Tracing then attaches those numbers to each LLM span for aggregation by turn, tool, role and user. Attribution comes from counting components in isolation (fixed prefix versus history) or from classifying messages, as nilenso's context-viewer does: on one agent, 41% of the window was regenerated output and 13% duplicated specs.

How to achieve it

  1. Fix the denominator. Read the model's input limit programmatically where possible (Gemini client.models.get(model).input_token_limit) and store it with the model id; tokenizers differ too (Claude 4.7 and later emit roughly 30% more tokens for the same text).
  2. Count before you send, on the exact payload, same model id, tools included. Anthropic's endpoint is free with its own rate limit; Gemini's count_tokens returns total_tokens. Use tiktoken only for OpenAI models.
  3. Read usage on every response and log input, output, cache-read and cache-creation tokens per turn. OpenAI exposes cache hits as usage.prompt_tokens_details.cached_tokens, Gemini as usage_metadata. The billed count is the ground truth.
  4. Attribute. Count the fixed prefix (system plus tool schemas) once per session and treat history as the remainder; tag each tool result with tool name and token size at insertion to see which tools dominate.
  5. Emit OpenTelemetry GenAI spans (invoke_agent, chat, execute_tool) with gen_ai.usage.input_tokens and gen_ai.usage.output_tokens, or send usage_details / usage_metadata to Langfuse or LangSmith, and aggregate per trace and per user via their metrics APIs.
  6. Alert on three signals: utilization thresholds (warn at 60%, force compaction at 80%), tokens added per turn, and a falling cache-read ratio, which usually means a supposedly stable prefix changed.
import anthropic

client = anthropic.Anthropic()
MODEL, WINDOW = "claude-opus-5", 200_000   # denominator: model's input limit

def measure(system, tools, messages):
    """Pre-send estimate (free endpoint, own rate limit); prefix vs history."""
    count = lambda msgs: client.messages.count_tokens(
        model=MODEL, system=system, tools=tools, messages=msgs).input_tokens
    total = count(messages)
    prefix = count([{"role": "user", "content": "x"}])  # system + tool schemas
    return {"total": total, "util": total / WINDOW,
            "prefix": prefix, "history": total - prefix}

def step(system, tools, messages):
    m = measure(system, tools, messages)
    if m["util"] > 0.60:
        raise RuntimeError(f"context at {m['util']:.0%}; compact before calling")
    resp = client.messages.create(model=MODEL, max_tokens=1024,
                                  system=system, tools=tools, messages=messages)
    u = resp.usage  # billed ground truth, read after every call
    record = {**m, "billed_in": u.input_tokens, "out": u.output_tokens,
              "cache_read": u.cache_read_input_tokens,
              "cache_write": u.cache_creation_input_tokens}
    emit(record)  # -> OTel gen_ai.usage.* span attrs, Langfuse, or LangSmith
    return resp

Trade-offs & pitfalls

  • Estimates are not bills. Counts may include unbilled system-added tokens, ignore earlier-turn thinking blocks, count server tools only on the first sampling call, and never apply caching; reconcile against usage after the call.
  • Tokenizer mismatch is the common silent error: tiktoken undercounts Claude text by roughly 15-20%, and Langfuse's Claude tokenizer fallback is flagged as inaccurate for Claude 3 and later. Count with the provider's tool for the model you will call.
  • Attribution can double count. Summing per-component counts duplicates shared wrapper text: Claude Code's /context reported about 45k tokens for an MCP server that measured 14-15k in one request (fixed January 2026); Langfuse requires each token to land in exactly one bucket.
  • Counting costs a round trip and a rate-limit slot (2,000 RPM at Anthropic's Start tier). Measure at decision points, not on every streamed token.
  • Numbers do not say what is redundant. OTel captures no prompt content by default, and classification views like context-viewer need raw messages and take about 40 seconds per 35k-token log; use them offline, not as a live gate.
